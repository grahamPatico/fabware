## 1. Plugin registration — `cadIrPlugin: ProcessPlugin<CadIr>`

**Status:** FAIL (BLOCKER)

**Evidence:**
- `artifacts/hardwareai/convex/cad/plugin.ts:81` exports `cadIrPlugin`.
- `artifacts/hardwareai/convex/plugins/index.ts:1-6` is the plugin-registry bootstrap. It registers ONLY `sheetMetalPlugin` via `_registerPlugin(sheetMetalPlugin)`. There is NO `_registerPlugin(cadIrPlugin)` call anywhere in the worktree.
- The plugin object IS imported and called from `convex/specialists/cadIr.ts:19` as a direct module import, NOT through the plugin registry.
- `cadIrPlugin.kind = "sheet_metal"` (`plugin.ts:84`) — same kind string as `sheetMetalPlugin`. Even if both were registered, the registry would collide on `kind`.

**Notes:** The CAD IR pipeline is reachable in production via a hardcoded fork inside `convex/orchestrator/tick.ts:85-92` (`if (partKind === "sheet_metal" && useCadIr) → schedule cadIr.run`), so the specialist runs and uses the plugin directly. But the plugin is NOT participating in the harness's pluggable dispatch contract — it shadows the sheet-metal plugin via the explicit if-branch. CADIR-01 acceptance ("ProcessPlugin<CadIr> is registered") is satisfied in spirit (specialist forks correctly behind `useCadIr`) but NOT through the canonical `_registerPlugin` surface. SUMMARY 01 is candid about this: "Phase 1 keeps `kind = sheet_metal` so the orchestrator's existing dispatch path works; Phase 2+ will introduce a dedicated `cad_ir` kind once all integration points support it." That follow-up never landed across phases 2–19.

## 3. Validation tier coverage — Tiers 1, 2, 3, 4, 5

**Status:** PARTIAL (WARNING — Tier 3 is bypassed in the plugin's `validate(...)`)

**Evidence:**
- All five tier files exist:
  - Tier 1: `convex/cad/validate/schemaTier.ts`
  - Tier 2: `convex/cad/validate/constraintTier.ts` (per `constraintTier.ts:3` "Tier 2 — Sketch Constraint Validation")
  - Tier 3: `convex/cad/validate/geometryTier.ts`
  - Tier 4: `convex/cad/validate/manufacturingTier.ts`
  - Tier 5: `convex/cad/validate/assemblyTier.ts`
- `manufacturingTier.ts` composes 10 rules including `holeEdgeDistance` (P1), `boltClearance` (P3), `minBendRadius` (P5), laser-cut/print/CNC (P14/16/17). `assemblyTier.ts` composes `partsInterfere` (P8) and `jointRangeCollision` (P11).
- The plugin's combined `validate(ir, ctx)` at `plugin.ts:34-79` invokes Tier 1 → Tier 2 → Tier 5 → Tier 4. **Tier 3 (geometry) is NOT called from `cadIrPlugin.validate`.**
- Tier 3 IS invoked, but only from `convex/specialists/cadIr.ts:308` after a successful sandbox execution (it consumes the sandbox `entities` artifact, which doesn't exist until build123d has run). So the specialist orchestrates Tier 3, but the plugin's `validate` does not.

**Notes:** Tier 3 wiring is structurally correct for the specialist's repair loop because Tier 3 needs sandbox `entities` to operate, but the plugin's `validate(...)` contract — which the harness would call if the plugin were registered through `_registerPlugin` — silently skips Tier 3. Combined with finding (1), this means: any future caller that goes through the plugin contract loses Tier 3. The mega-integration test (`integration-final.test.ts`) also does NOT exercise Tier 3 (it never runs the sandbox executor), so Tier 3 has only `__tests__` unit coverage, not E2E coverage. Phase 1 SUMMARY claims Tier-3 is part of the foundation; it is, but it lives outside the plugin's `validate` boundary.

## High-level summary

The 19-phase CAD IR rebuild ships a coherent, well-typed, well-tested type/IR/validate/codegen stack with comprehensive unit test coverage and a single-file mega-integration test (`integration-final.test.ts`) that exercises all five validation tiers and all five compile targets in one pass. Internal API surfaces (Tiers 1/2/3/4/5, build123d/URDF/MJCF/BOM/cost compilers, 12-tool patch grammar, process-gated MFG rules, joint sampler, AABB interference, STEP import codegen) are real, exported, and consume one another correctly at the typecheck layer. **However, the rebuild has three integration gaps that compromise the milestone-level cutover gate.** First, `cadIrPlugin` is never registered through `_registerPlugin` — it ships as a direct module import inside the orchestrator's hardcoded `if (useCadIr)` fork, and its `validate(...)` skips Tier 3 (geometry validation only runs from inside the specialist after sandbox execution). Second, four of the five compile targets (URDF, MJCF, BOM, cost/fabricationCost/machineCost, compileAssembly) are reachable only from the mega-integration test — the live specialist's runtime path only invokes `compileToBuild123d`, so phases 4/5/6/9/10/12/13's compile outputs are never persisted, exposed via Convex queries, or rendered in the UI. Third, and most critically, **CADIR-02 (glTF preview parity) is broken end-to-end**: the sandbox emits a glb artifact, but the specialist never persists `sandboxResult.glb` (the `glbStorageId` schema field is dead code), no Convex query exposes a `glbUrl`, the `CadPreview` component is an orphaned export imported nowhere in `src/`, and the production `AssembledView`/`Workspace` components have no fork on `useCadIr`. Combined with the absence of any UI control to flip `useCadIr` (CUTOVER-02), the user-facing acceptance flow ("toggle useCadIr=true → see glTF previews → run tennis-ball-locker") is unreachable through the React app from this build state — verification has been editorial/manual only, as `19-VALIDATION.md` candidly documents. The codebase is internally consistent and the agent loop converges; the milestone cutover surfaces are not.
