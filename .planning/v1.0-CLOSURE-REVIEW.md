**Reviewed:** 2026-05-07

## Summary

The four closure commits achieve their stated goals: (a) `cad_ir` is now a real
PartKind with registry-driven dispatch, (b) the live compile pipeline is wired
in and persists artifacts, (c) `stepUrl` survives the agent → patch → applyPatch
→ compileAssembly chain, (d) the stale orchestrator comment is corrected. The
`stepUrl` round-trip test is genuinely end-to-end and validates the EXTERNAL-01
consumer.

However the GLB persistence path contains a runtime-fatal Convex bug
(`Buffer.from` in a non-`"use node"` action), and the live compile pipeline
pairs a stale GLB with the final IR in several plausible scenarios. There are
also a handful of medium-severity correctness issues around schema/PartKind
divergence, repair-loop error handling, and a redundant double-compile of
fabrication+machine cost. Frontend toggle UX is acceptable but rough.

The chore commit (05fe0eb) is a pure comment refresh — verified accurate.

## CRITICAL

### CR-01: `_storeGlbBlob` uses Node-only `Buffer.from` from a V8-runtime action — will throw at runtime

**File:** `artifacts/hardwareai/convex/specialists/cadIrInternals.ts:199-207`

The action is declared in a file that explicitly does NOT have `"use node"`
(see the file-header comment at line 4-6, which states the file MUST run in
the standard Convex runtime so its queries/mutations are valid). In the
default Convex V8 runtime, `Buffer` is not a global — only Web APIs
(`Uint8Array`, `atob`, `Blob`) are available. The first time the cadIr
specialist invokes `internal.specialists.cadIrInternals._storeGlbBlob`, the
handler will throw `ReferenceError: Buffer is not defined` (or equivalent),
the `try/catch` in `cadIr.ts:228-238` will swallow it, the GLB will silently
not persist, and the user will never see a CAD IR preview. The "happy path"
of the entire feature is broken.

This is not caught by tests because no test invokes the action through the
real Convex runtime — `cadIrInternals.ts` does not appear to be unit-tested,
and the `toolCallToPatch` round-trip test stops at `compileAssembly`.

**Fix:** Move `_storeGlbBlob` into its own file with `"use node";` at the top,
OR rewrite the decode using Web APIs available in the V8 runtime:

```typescript
// V8-runtime safe decode (no "use node" needed):
export const _storeGlbBlob = internalAction({
  args: { base64: v.string() },
  handler: async (ctx, args): Promise<Id<"_storage">> => {
    const binary = atob(args.base64);
    const bytes = new Uint8Array(binary.length);
    for (let i = 0; i < binary.length; i++) bytes[i] = binary.charCodeAt(i);
    const blob = new Blob([bytes], { type: "model/gltf-binary" });
    return await ctx.storage.store(blob);
  },
});
```

Either fix is fine; the file-split route is cleaner because it preserves the
file's documented invariant (queries/mutations stay in V8 runtime, node-only
work moves to a node module).

## HIGH

### HI-01: Persisted GLB can be desynced from persisted IR (stale-preview bug)

**File:** `artifacts/hardwareai/convex/specialists/cadIr.ts:108-191, 226-239, 318-328`

The repair loop runs the sandbox conditionally — only when `pluginViolations`
is empty (line 114). It captures `lastSandboxGlb = sandboxResult.glb`. The
loop can then exit with the IR mutated again by an agent repair turn that
fixed geometry violations, then schema/manufacturing failed on the next
iteration, exhausting `TURN_BUDGET` without re-running the sandbox. Two
concrete trajectories that produce a stale GLB:

1. Turn 0: validate clean → sandbox runs → captures GLB(IR_0) → geom violations →
   agent fixes them → IR_1.
2. Turn 1: validate(IR_1) finds tier-1 schema violation → agent attempts repair →
   IR_2 is produced but still violates → loop continues.
3. Turn N (= TURN_BUDGET): exit with `finalViolations.length > 0`, persist
   `currentIr = IR_2` AND `lastSandboxGlb` from `IR_0`. The 4b path
   (line 318-328) writes that mismatched GLB to the artifacts row.

UI consumers (CadPreview + headRevisionArtifacts) will then render geometry
that does not match the IR snapshot, with no signal that they are mismatched.

**Fix:** Track which IR hash the captured GLB belongs to. Only persist the GLB
when the captured-for-hash matches the final-persisted hash, or store the
generating-IR hash on the artifacts row alongside the storage id and have
consumers verify before rendering.

```typescript
let lastSandboxGlbForHash: string | null = null;
// ...inside the sandbox branch...
lastSandboxGlb = sandboxResult.glb;
lastSandboxGlbForHash = hashIr(currentIr); // track the IR that produced it
// ...at persist time...
if (lastSandboxGlb && lastSandboxGlbForHash === irHash) {
  // safe to persist
}
```

### HI-02: Repair loop has no top-level error handler — `runSandbox` failures strand the part in `designing` forever

**File:** `artifacts/hardwareai/convex/specialists/cadIr.ts:133`

`runSandbox(scriptPython)` can throw on (a) Vercel Sandbox provisioning
failure, (b) network errors, (c) pip install failures during boot, (d) any
unexpected error in `_readBase64`/`_readText` other than the wrapped ENOENT
case. There is no `try/catch` around the call. If it throws, the action
handler bubbles the error before `_writeRevision` runs and before
`_setPartStatus` sets the final status. The part stays at `status: "designing"`,
which is precisely the status that the orchestrator's status-guard
(tick.ts:71-75) uses to suppress re-dispatch. The part is now permanently
stuck — no new tick will retry it, no escalation is opened.

**Fix:** Wrap the loop body (or at minimum the sandbox call) in `try/catch`,
and on failure persist a `failed` revision + `escalated` part status with a
synthetic infrastructure violation:

```typescript
try {
  const sandboxResult = await runSandbox(scriptPython);
  // ...
} catch (err) {
  finalViolations = [{
    ruleId: "infra.sandbox-error",
    severity: "error",
    message: "Sandbox execution failed",
    agentMessage: `The geometry sandbox could not run: ${err instanceof Error ? err.message : String(err)}`,
  }];
  break;
}
```

### HI-03: `PartKind` union and `parts.kind` schema have diverged — `cad_ir` is not actually persistable

**Files:**
- `artifacts/hardwareai/convex/plugins/types.ts:10`
- `artifacts/hardwareai/convex/schema.ts:83-87`
- `artifacts/hardwareai/convex/lib/partKind.ts:24`

`PartKind` is now `"sheet_metal" | "printed" | "purchased" | "cad_ir"` and
`PART_KIND_LABEL.cad_ir = "CAD IR"` exists. But `parts.kind` in schema.ts
remains restricted to the three legacy literals — there is no
`v.literal("cad_ir")` slot. Any attempt to write `kind: "cad_ir"` to a part
row will be rejected by Convex's schema validator at write time.

In practice the closure design dispatches `cad_ir` through the `useCadIr=true`
flag on a `kind: "sheet_metal"` part, so this works today. But:

1. `_loadPartAndProject` casts `(p.kind ?? "sheet_metal") as PartKind` — the
   cast is sound because the schema guarantees the read value is one of the
   three legacy kinds.
2. `computeNextAction` accepts `kind` from the Doc and tests
   `registeredKinds.includes(kind)`. This works fine — but the inconsistency
   between the runtime universe (3 kinds) and the type universe (4 kinds) is a
   trap for future code.
3. `PART_KIND_LABEL` declares a key for a state that cannot exist in the DB.
   Any UI that tries to read `PART_KIND_LABEL[part.kind]` won't break, but
   the "CAD IR" label is unreachable.

**Fix:** Either (a) extend `parts.kind` schema to accept `v.literal("cad_ir")`
if you actually want a part to carry `kind: "cad_ir"` directly (and migrate
the dispatcher off `useCadIr=true`), or (b) remove `cad_ir` from the canonical
`PartKind` union since it is in fact a *plugin* identifier, not a
*part-row* identifier — only the `getPlugin(...)` registry needs to know
about it. The current state is the worst of both.

### HI-04: `CadIrPartContext` cast in `validate(...)` is structurally unsound when callers omit `sandbox`

**File:** `artifacts/hardwareai/convex/cad/plugin.ts:60`

```typescript
const sandbox = (ctx as CadIrPartContext).sandbox;
```

This is fine *today* because `CadIrPartContext extends PartContext` adds only
the optional `sandbox` field, so reading it from a bare `PartContext` returns
`undefined`. But TypeScript's `extends + optional` does not actually guarantee
this at runtime: a future refactor that makes `CadIrPartContext` add a
*required* field (e.g. `sandbox: { ... }`) would compile fine here yet crash
generic plugin hosts that pass a bare `PartContext`. The cast also defeats
TS's variance checks — the contract should either widen `validate(ir, ctx)`
to accept the optional `sandbox` directly, or the plugin should expose a
separate API and not rely on a covariant cast.

This is the "latent type-safety hole" the focus_areas asked us to confirm or
call out — calling it out.

**Fix:** Lift `sandbox` into the canonical `PartContext` as an optional
escape-hatch field:

```typescript
// plugins/types.ts
export interface PartContext {
  scope: unknown | null;
  peerParts: Array<{ partId: string; label: string; kind: PartKind }>;
  /** Plugin-specific extensions. CAD IR uses `sandbox`. */
  pluginContext?: Record<string, unknown>;
}
```

Or add an explicit `validateWithSandbox` on the CAD IR plugin that the
specialist calls directly (bypassing the generic `validate` entry point). Both
make the contract honest. The current cast hides the dependency.

## MEDIUM

### ME-01: `cost.ts` already invokes `compileFabricationCost` and `compileMachineCost`; specialist re-runs them

**File:** `artifacts/hardwareai/convex/specialists/cadIr.ts:277-296`
plus `artifacts/hardwareai/convex/cad/compile/cost.ts:158-163`

`compileCost(currentIr, BUILTIN_PRICING)` internally calls
`compileFabricationCost(ir)` and `compileMachineCost(ir)`. The specialist then
calls them a second time on lines 285 and 292 to populate
`fabricationCostJson` and `machineCostJson`. This isn't a correctness bug —
both functions are pure — but it doubles the work for parts with non-trivial
fabrication graphs. More importantly, if the two invocations ever drift
(different signatures, different config), the specialist's persisted JSON
will not match what `costJson` already contains.

**Fix:** Persist the components from the existing `costResult`:

```typescript
const costResult = compileCost(currentIr, BUILTIN_PRICING);
costJson = costResult;
fabricationCostJson = { totalUsd: costResult.fabricationTotalUsd };
machineCostJson = { perPart: costResult.machine };
```

Or remove the separate `fabricationCostJson` / `machineCostJson` columns from
`cad_revision_artifacts` and let consumers project them out of `costJson`.

### ME-02: Failed-path artifact persistence drops everything except GLB — URDF/MJCF/BOM never appear for escalated parts

**File:** `artifacts/hardwareai/convex/specialists/cadIr.ts:316-339`

When `finalViolations.length > 0`, the only artifact persisted is the (likely
stale, see HI-01) GLB. The branch never attempts to compile URDF/MJCF/BOM/cost
even though for many "escalated" parts the IR is structurally valid (e.g.
hole-edge-distance manufacturing warning) and these artifacts would still be
useful for downstream review. The intent is unclear from the code.

**Fix:** Either (a) explicitly document why escalated parts get no
post-execution artifacts (current code reads as "skipped because we ran out
of repair budget"), or (b) duplicate the success-path compile block so
escalated parts still get URDF/MJCF/BOM/cost when the IR resolves cleanly.

### ME-03: `runSandbox` can return `ok: false` — specialist treats it as success and runs Tier 3 anyway

**File:** `artifacts/hardwareai/convex/specialists/cadIr.ts:133-148`

`runSandbox` returns `{ ok: boolean, log, entities, step, glb }`. `ok` is
`exitCode === 0`. The specialist ignores `ok`. If the script crashed (exit
code != 0), `entities` is `[]`, `log` contains the Python traceback, and the
geometry-tier validator runs against empty entities — it will probably emit a
"missing face tags" violation and the agent will be asked to repair geometry
that never compiled. The agent will, of course, not know what to do.

**Fix:** Guard on `ok`:

```typescript
if (!sandboxResult.ok) {
  finalViolations = [{
    ruleId: "geom.build-failed",
    severity: "error",
    message: "Geometry sandbox build failed",
    agentMessage: `Build123d execution failed:\n${sandboxResult.log.slice(0, 800)}`,
  }];
  // skip Tier 3, proceed to repair-or-bail
}
```

### ME-04: AssembledView toggle has no graceful-degradation message when `useCadIr=true` but no GLB exists

**File:** `artifacts/hardwareai/src/components/workspace/AssembledView.tsx:345-354`

The CAD IR overlay only renders when *all three* of
`focusedPart && focusedPartUseCadIr && cadArtifacts?.glbUrl` are truthy. A
user who toggles `useCadIr` on a legacy part (no head revision yet, or a head
revision predating the gap-closure commits, or a revision that failed) sees
nothing — no overlay, no spinner, no "preview not yet available" hint. The
toggle silently appears to do nothing, which is the worst UX outcome for a
"developer flag."

The toggle also writes through `setUseCadIr` immediately, which schedules a
`tick` (projects.ts:251). On legacy parts with status `"ok"` the tick is a
no-op (the orchestrator only re-dispatches `pending` parts), so toggling on
will not produce a CAD IR revision unless the part is also reset to pending.
There is no UI indication of this.

**Fix:** When `focusedPartUseCadIr === true` but `cadArtifacts?.glbUrl` is
absent, render a placeholder card with a one-line message: "CAD IR preview
not available — re-run the part to produce one." Optionally, also add a
"Re-run" button that flips the part status back to `pending`.

### ME-05: `validate(...)` returns inconsistent shapes depending on whether sandbox is provided

**File:** `artifacts/hardwareai/convex/cad/plugin.ts:82-91, 111`

When `sandbox` is provided AND geometry violations exist, the function
returns ONLY `geomViolations` (line 89), discarding all of:
- constraint warnings (`constraintViolations` filtered to non-error severity)
- manufacturing/budget violations from Tier 4

When `sandbox` is omitted, the function eventually returns
`[...t2, ...mfgAndBudget]` which DOES include those. So the same IR validated
against the same context with vs. without `sandbox` returns disjoint subsets
of violations. Callers cannot treat these as equivalent.

**Fix:** Always concatenate violations from all tiers that ran, only
short-circuiting on hard schema-tier failures (already correct on line 63-65).
This is a behavioral change that may need to thread through the agent prompt
template.

## LOW

### LO-01: `_loadPartAndProject` reuses `partId` as `projectId` on the not-found path

**File:** `artifacts/hardwareai/convex/specialists/cadIr.ts:65-71`

```typescript
if (!part) {
  await ctx.scheduler.runAfter(0, internal.orchestrator.tick.tick, {
    projectId: args.partId as unknown as Id<"projects">,
  });
  return { status: "skipped", reason: "part not found" } as const;
}
```

When the part has been deleted, the tick is dispatched against a *part id*
that's been recast as a *project id*. `_internalTickContext` will look it up
as a project, get `null`, and return a "wait" — so this is a no-op in
practice — but it logs misleading data and burns a scheduler slot. There is
no way to recover the projectId once the part is gone (the part row is the
only join key), so the cleanest fix is to simply not re-tick at all here.

**Fix:** Remove the `runAfter` call; just return.

### LO-02: `headRevisionHash` non-null assertion in queries

**Files:**
- `artifacts/hardwareai/convex/cad/queries.ts:29` — `q.eq("hash", part.headRevisionHash!)`
- `artifacts/hardwareai/convex/specialists/cadIrInternals.ts:51` — same pattern

Both query handlers check `if (!part?.headRevisionHash) return null;` and then
pass `part.headRevisionHash!`. The `!` is technically redundant (TypeScript
should narrow), but the pattern survives narrow-loss across the optional-chain
into the closure passed to `withIndex`. Cosmetic, not a bug.

**Fix:** Hoist the value:

```typescript
const headHash = part.headRevisionHash;
if (!headHash) return null;
const rev = await ctx.db.query("cad_revisions")
  .withIndex("by_part_hash", (q) => q.eq("partId", partId).eq("hash", headHash))
  .first();
```

### LO-03: `_setPartStatus` resolved through `sheetMetalInternals`

**File:** `artifacts/hardwareai/convex/orchestrator/tick.ts:72-75`

The CAD IR dispatch path (line 96-98) schedules `internal.specialists.cadIr.run`
for the cad_ir branch — but the *pre-dispatch status update* on line 72-75
calls `internal.specialists.sheetMetalInternals._setPartStatus`. This works
because both internals files export the same mutation against the same table,
but it means a refactor that splits the two mutations (e.g. logging different
metadata per kind) would silently break the cad_ir path. The orchestrator
should not be reaching into a kind-specific internals module.

**Fix:** Move `_setPartStatus` to a shared module
(`convex/specialists/_shared.ts` or similar), or have each specialist's
internals file export its own and route through `getPlugin(kind)`-derived
dispatch.

### LO-04: New `headRevisionArtifacts` and `revisionGlbUrl` queries are public — no access control

**File:** `artifacts/hardwareai/convex/cad/queries.ts:20, 60`

Both queries are declared via `query({...})` not `internalQuery({...})`,
making them callable from any client given a `partId`. There is no
`ctx.auth.getUserIdentity()` check, no project-membership verification, and
the returned `glbUrl` is a Convex storage URL that requires no further auth
to fetch. Anyone who knows or guesses a `partId` can read the geometry of any
part across any project.

This is consistent with the rest of the codebase — `grep -r ctx.auth
artifacts/hardwareai/convex` returns nothing — so it is not a regression from
these commits. But it is a real exposure surface and the new queries widen
it (geometry artifacts are now publicly fetchable). Worth flagging for a
follow-up auth pass before any non-internal launch.

**Fix:** When auth lands, gate both queries on project-membership:

```typescript
const identity = await ctx.auth.getUserIdentity();
if (!identity) return null;
// ...verify identity has read access to part.projectId...
```

### NI-02: Comment on cadIr.ts:38 declares `TURN_BUDGET = 3` with no rationale

**File:** `artifacts/hardwareai/convex/specialists/cadIr.ts:39`

Magic number with no comment. A budget of 3 means up to 4 sandbox runs per
specialist invocation (turns 0–3), which at ~30s each is a couple of minutes
of latency in the worst case. Fine for v1, but worth a one-line explanation
of the choice.

**Fix:** Add a comment: `// 3 turns × ~30s sandbox = ~2min p99 latency budget`.
